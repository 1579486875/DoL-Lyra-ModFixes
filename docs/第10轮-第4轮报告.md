## 一、修的问题（1 处）

### `npcexposetext` widget 中英混杂

```do
<!-- 修前 -->
<<set _text_output to "The " + _person + " 掀起 " + _his + " skirt, ">>
<!-- 修后 -->
<<set _text_output to _person + "掀起" + _his + "的裙子，">>
```

**影响**：NPC 暴露你的场景里，玩家会看到
`The 惠特尼 掀起 她的 skirt, 露出湿润的小穴。`

**这是「中英混杂」的典型形态** —— 句子骨架是英文，中间被机器翻译替换了部分词。

## 二、澄清的三个「伪问题」（重要）

### ① `/* */` 在 passage 正文里有 3611 处 —— **不是 bug**

| | 数量 |
|---|---|
| 基线 | 3610 |
| 当前 | 3611（+1 是我 R10 注入的 `catch (e) { /* ignore */ }`）|

**结论**：原版 DoL 大量用 `/* */` 作 passage 内注释，**SugarCube 不会把它们当文本输出**。
（否则原版游戏就会有 3600 处英文注释文字，不可能）

**教训**：**不要把「原版就这样」的东西当 bug 修。**

### ② `<<case>>` 值含中文 19 处 —— **是设计如此**

```do
<<case "咖啡">>        ← $coffee 变量存的就是「咖啡」
<<case "不深不浅" "r不深不浅" "ymedium" "gmedium" "bmedium">>   ← 混合形态
```

**基线也是 19 处，逐个对得上**。

**原因**：`<<switch>>` 对比的变量本身就是中文（`$coffee` 存「焦糖拿铁」），
所以 case 值写中文是**正确的**。

**但 `"不深不浅"` 和 `"ymedium"` 混在一起**看起来可疑 —— 这是**原版遗留**，不动。

**教训**：**「值含中文」不等于「被误翻」，要看被 switch 的变量本身是什么语言。**

### ③ `widget 顶层裸英文 191 处` —— **全是 `/* 注释 */`**

误报。我的判据排除了 `<` 开头的行，但没排除 `/*`。

## 五、本轮的方法论收获

**「伪问题」比「真问题」更耗时。**

本轮花最多时间的不是修 bug，而是**确认三个东西不是 bug**：

| 伪问题 | 为什么像 bug | 怎么排除的 |
|---|---|---|
| `/* */` 3611 处 | 在 SugarCube 里 JS 注释语法确实不是注释 | **对比基线：3610 vs 3611，一致** |
| `<<case>>` 值含中文 | 值被翻译会导致匹配失败 | **对比基线：19 vs 19，一致** |
| widget 顶层 191 处英文 | 看起来像裸输出 | **逐个看：全是 `/* */`** |

**共同点：都是「对比基线」这一招解决的。**

**所以模板里那条「任何『这个是不是本来就有』的疑问，先 diff 基线」要加粗。**
