## ⚠️ 失败的尝试

### BG23：翻译表重复赋值修复（已回滚）

**目标**：修复 4 个翻译表的重复赋值问题
- NPCTypeList_cn_name：2 次赋值
- CafeFoodList_cn_name：2 次赋值
- NPCNameList_cn_name：2 次赋值
- NPCTitleList_cn_name：2 次赋值

**问题分析**：
- 第 1 次赋值和第 2 次赋值内容不同
- 第 2 次赋值会覆盖第 1 次，导致数据丢失
- 总共丢失约 195 个翻译条目

**修复尝试**：
1. 提取两次赋值的内容
2. 合并成一个字典（第 2 次的值覆盖第 1 次）
3. 将合并后的内容替换第 2 次赋值
4. 删除第 1 次赋值

**失败原因**：
使用 `H.unescape(raw)` 处理整个 HTML 导致**灾难性后果**：
- **破坏了 16,084 个 passage 的 HTML 编码**
- 所有 `&lt;&gt;` 都变成了裸的 `<>`
- C.no_raw_angle_in_passage 从 0 激增到 16,084

**回滚操作**：
- 恢复到 BG22 之后的备份（backup_143407）
- 通过率从 66/90 恢复到 67/90
- 重新执行 BG22，恢复到 68/90

**教训**：
1. **绝对不能对整个 HTML 使用 unescape**
2. 只能在局部、特定的 passage 或脚本块内操作
3. 重复赋值问题需要更安全的修复策略
4. 或者暂时搁置，等待更好的解决方案

## 🎓 经验教训

### 成功经验

1. **局部修复优于全局修复**
   - BG24（模板字符串粘连）：只在特定字符串上操作
   - BG25（双重转义）：只在特定 passage 内操作
   - 风险可控，影响面小

2. **在 raw HTML 中操作，避免 unescape**
   - 除非必要，不要对整个 HTML 使用 unescape
   - 如果必须 unescape，只处理特定的 passage 或脚本块

3. **充分验证后再替换**
   - 每个修复脚本都包含验证逻辑
   - 修复前后都进行检查
   - 与 vanilla 版本比对（如 BG25）

4. **完善的备份机制**
   - 每次修复前都创建带时间戳的备份
   - 失败时可以快速回滚
   - BG23 的回滚就是靠备份机制

### 失败教训

1. **BG23 的灾难性失败**
   - **错误做法**：`fixed = H.unescape(raw)` 然后直接保存
   - **后果**：破坏 16,084 个 passage 的 HTML 编码
   - **正确做法**：只在特定区域 unescape，或者在 raw HTML 中直接操作

2. **重复赋值问题的复杂性**
   - 看似简单的"合并两次赋值"，实际上涉及：
     - HTML 编码问题
     - 上下文依赖
     - 潜在的副作用
   - **建议**：暂时搁置，等待更安全的解决方案

3. **假阳性的识别**
   - F 类中很多"失败项"实际上是游戏正常逻辑
   - 例如：`_sydtext is "Sydney"` 是游戏中的条件判断
   - **建议**：在 REGRESS_ALL.py 中标记豁免，而不是修改游戏代码
